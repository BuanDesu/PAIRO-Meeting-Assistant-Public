# P2P Meeting Copilot — MVP 实施计划

## 目标
构建一个桌面浏览器与手机浏览器协作的个人会议助手：桌面端主动共享屏幕/可选系统音频和麦克风，快捷键截屏或启动语音识别；手机端接收 WebRTC 媒体和请求，显示桌面画面，并可用用户自带的 OpenAI-compatible LLM API 回答。

## 架构
- **桌面/手机前端**：Vite + 原生 JavaScript，响应式单页应用。桌面端负责浏览器授权、getDisplayMedia、麦克风、Web Speech Recognition 和快捷键；手机端负责媒体播放、对话视图、LLM 设置与回复。
- **媒体/消息传输**：WebRTC RTCPeerConnection 传递音视频，RTCDataChannel 传递截图、转写文本和回复。屏幕帧与问卷图像不经过信令服务。
- **信令**：Node.js + ws 仅转发 SDP/ICE；房间限桌面端+手机端各一位成员，断开后清理，不持久化房间。默认 STUN；严格 NAT 环境需部署 TURN。
- **模型**：手机浏览器直连用户配置的 OpenAI-compatible Chat Completions endpoint；API Key 只保存在运行时内存，不写入服务器、信令或浏览器持久存储。

## 交互
1. 桌面端生成一次性房间码，开启屏幕分享并展示配对码。
2. 手机输入信令地址与房间码，建立 WebRTC 连接。
3. Alt+Shift+S 发送当前共享屏幕截图；Alt+Shift+M 切换语音识别，识别到的问题可自动或手动提交到手机 AI。
4. Alt+Shift+A 可经 DataChannel 切换手机自动回答；手机可对截图/文本生成答案，并将回复同步回桌面端。

## 隐私与边界
- 需由用户主动选择分享屏幕/麦克风；切换标签或浏览器策略可能停止捕获。
- 浏览器语音识别在部分浏览器会使用厂商在线服务；UI 与文档会明确提示。
- API Key 不持久化；LLM 请求直接从手机浏览器发往提供商，因此提供商及网络仍可看到提交的内容。
- WebRTC 的加密 P2P 不保证所有网络都能直连；生产部署应使用 HTTPS/WSS 和有访问控制的 TURN 服务。
- 浏览器限制：需要支持 WebRTC、WebSocket、屏幕捕获的桌面 Chromium 浏览器；移动端音频通常需用户点击播放。

## 验收
- 桌面与手机用同一房间码完成 offer/answer/ICE 交换。
- 手机能实时看到共享桌面并手势开启音频。
- 桌面快捷键能发送压缩截图和转写文本；手机能显示并提交问题给配置的模型。
- 模型回复显示在手机和桌面端；没有 API Key 时显示可恢复的配置提示。
- 信令服务仅转发连接协商消息，不存储/转发屏幕帧、录音、LLM Key 或提示内容。
